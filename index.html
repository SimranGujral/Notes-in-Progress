Designing an On-Call Service

Functional Requirements

  • The system should create on-call schedules for an organization's services.
  • The system should define an escalation matrix during a CSO.
  • The system should notify service owners according to the escalation matrix and progress through escalation layers when needed.

Non-Functional Requirements

Availability

The scheduling service runs in the control plane. Scheduling work can be deferred during an outage, so the service can target 99.9% availability (about 8 hours and 46 minutes of downtime per year, or roughly 44 minutes per month).

The escalation engine needs higher availability because service owners must be notified quickly during an outage. It should target at least 99.99% availability (a maximum of about 53 minutes of downtime per year, or roughly 4.4 minutes per month).

The scheduling service produces an artifact used by the escalation engine. Replicate this artifact so it remains available to the escalation engine even when the scheduling service is down.

Consistency

Updates to the same service and shift must be applied sequentially when multiple people edit concurrently. No shift should be left unmanned, so schedule writes require strong consistency.

Updates to read replicas can be asynchronous and eventually consistent, allowing the escalation engine to read a stable schedule snapshot while a schedule is being updated.

Read/Write Ratio

Scheduling service: Assume each service has one schedule artifact that is created or refreshed once every three months, and experiences about one incident per month. This gives approximately four schedule writes and at least 12 incident-triggered reads per service per year, excluding UI loads and edits, or a baseline of about 3:1 reads to schedule writes. For capacity planning, use an estimated overall read-to-write ratio of 100:1 to account for additional reads such as UI loads and edits; validate it against expected traffic and incident-processing behavior.

Escalation engine: The escalation engine uses the schedule artifact produced by the scheduling engine. During an incident:

  • An incident record is created.
  • The escalation matrix is fetched for each impacted service; a single incident may affect multiple services resulting in a fan out per incident.
  • A record is created for each affected service, either a single record with information about each escalation layer or multiple records. If layers are stored in multiple records in the scheduling artifact it might make sense to do a fetch only if the current layer does not acknowledge a notification. The acknowledgement status is updated at each layer.

Based on these assumptions, the read-to-write ratio is approximately 1:1.

Scale

Assume 100 organizations with 1,000 services each: 100,000 services requiring rosters. If roster creation happens every three months, the expected scheduling and incident workloads are:

Schedule creation

  • 100,000 roster requests every three months.
  • For each three-month schedule refresh, assuming 3 layers, 2 shifts per layer, and about 100 days of coverage, each request produces about 600 writes.
  • 600 × 100,000 ÷ 3 ≈ 20 million writes per month, or about 6 writes per second on average.

Average write throughput can obscure the peak load. If all 100,000 service schedules are refreshed at the start of a quarter, and each refresh generates approximately 600 schedule-entry writes, the system must process up to 60 million writes during that refresh. The scheduling pipeline should accept refresh requests through a queue and process them at a controlled rate, with capacity sized to the required completion window. Publish each completed schedule artifact atomically so the escalation engine never reads a partially generated schedule.

Incident processing

Assume 100,000 incidents per month. For a high-impact incident affecting up to 100 services, the estimate per incident is:

  • About 1 write for affected-service records.
  • For every service, it would have a maximum of 3 fetches for escalation data.
  • For every service, it would have a maximum of 3 writes for writing the escalation data.
  • For every service, it would have a maximum of 3 acknowledgement and polling updates.
  • For every service about 3 transactional outbox writes for three layers

This is approximately 1,300 database operations per incident. At 100,000 incidents per month, that is around 100 million operations per month, or roughly 50 operations per second on average.

A broad cloud-provider outage could affect many services across many tenants at once. Consider tenant-based partitioning, tenant-service keys to ease search for on calls during an outage of a wider scale.

Core Entities

  • Services
  • Users
  • Escalation layers
  • Shifts
  • Schedules
  • CSOs and affected services

Relationships

  • A service has many escalation layers.
  • An escalation layer has many users and many shifts.
  • A user is assigned to a shift; a shift has schedule entries.
  • A CSO can affect multiple services.

For example, a billing service might have primary, secondary, and tertiary escalation layers. The primary and secondary layers could each have two shifts, while the tertiary layer has one. A shift groups people into a particular rotation; schedule entries specify who is on call during a particular time interval.

The ongoing-CSO data can be represented as a CSO record plus one affected-service record per service. Each affected-service record tracks the current layer, acknowledgement state, notification start time, next escalation time, attempt count, and whether it is the last layer.

Scheduling System

  1. Configure each service's layers, shifts, shift times, and time between escalations.
  2. Set the schedule calendar length to three months and regenerate or refresh the schedule every three months.
  3. Calculate the number of rotations from the calendar length and rotation length.
  4. For each layer and shift, assign team members in rotation order and create schedule entries for each rotation.
  5. Store each entry with its layer, shift, on-call assignee, and start/end interval.

Schedule creation produces the artifact consumed by the escalation engine. Replicas of this artifact should remain readable if the scheduling service becomes unavailable.

Escalation System

  1. When a CSO is triggered, create an active CSO record and list the affected services.
  2. Create an affected-service record at the first escalation layer for each impacted service.
  3. Send a notification event for the first layer, then record the notification start time and increment the attempt count.
  4. Run a scheduler every minute. If the current layer has not been acknowledged and its escalation time has been reached, create a record for the next layer, mark the previous layer as no longer current, and notify the new layer.
  5. Continue through the layers. At the final layer, retry according to policy or route the incident for manual intervention.

Fetch on-call snapshots for each affected service and layer, including the on-call owner and shift end time, so the escalation engine can continue without depending on live scheduling-service availability.

Reliability Considerations

Atomicity

Notification publishing and updating the corresponding layer record must stay consistent. Use a transactional outbox so the notification event and its state change can be reliably coordinated and retried.

Idempotency

Notification publishing must be safe to retry. Repeated requests with the same idempotency key should return the existing notification ID rather than creating duplicate notifications.
