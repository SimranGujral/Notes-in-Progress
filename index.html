Designing an On-Call Service

Functional Requirements

  • The system should create on-call schedules for an organization's services.
  • The system should define an escalation matrix for each service.
  • The system should notify service owners according to the escalation matrix and progress through escalation layers when needed.

Schedule Generation Workflow

  1. Save the schedule rules. When a user sets up or changes a service's schedule, save the rules and a due outbox event together in one database transaction. Give the rules a version so the event uses the right version later.
  2. Publish due work. A worker claims a due outbox row with a lease so another worker does not process it at the same time, then publishes its event to the schedule queue. Mark it published after the queue confirms receipt. If the worker fails before marking it, it may publish the event again.
  3. Expect retries. The same event may arrive more than once, so the consumer uses its stable event ID to recognize duplicates.
  4. Build the roster. The consumer loads the rules version named in the event and works out who is on call for each layer and shift during the requested period.
  5. Save everything together. In one database transaction, save all roster rows, record the event as processed, mark the schedule event complete, and add the next run to the outbox. Enforce a unique processed-event ID so retries cannot create a duplicate roster.
  6. Confirm success. Acknowledge the queue message only after the transaction commits. If saving fails, roll back and retry. If the event was already processed, make no changes and acknowledge the duplicate.

The database transaction protects the roster and related records. Queue publication happens outside that transaction, so the outbox and idempotent consumer handle retries across the database and queue.

Escalation Service Workflow

  1. Create the incident. In one database transaction, save the incident, one impacted-service row for each affected service, and a layer 1 event in the outbox. Keep one impacted-service row per (incident_id, service_id).
  2. Publish due work. An outbox worker claims due events with a lease, publishes them to the queue, and marks them published after the queue confirms receipt. If it fails before recording publication, the same event may be published again, so each event needs a stable ID.
  3. Find the on-call person. The consumer ignores event IDs it has already processed. It looks up the person for that service and layer in the roster, then—in one transaction—creates a notification row, updates the impacted-service row with the current layer and notification, marks the outbox event complete, and records the event as processed. Use a unique key for (impacted_service_id, layer, attempt).
  4. Send the notification. A dispatcher sends pending notification rows to the external notification system using the notification ID as an idempotency key, if the provider supports it. After confirmation, it records the notification as published, sets the impacted service to waiting_for_ack, and adds a delayed escalation event to the outbox in one database transaction. Keep delivery state (pending or published) separate from acknowledgement state (pending, acknowledged, or no_ack).
  5. Wait, then decide whether to escalate. When the delayed event is due, check that it still refers to the current notification. In one transaction, record the event as processed and mark its outbox row complete. If the notification was acknowledged, mark the impacted-service row complete. Otherwise, mark the notification no_ack and move to the next layer. If another layer remains, add its event to the outbox in the same transaction.
  6. Record acknowledgements. The external system sends an acknowledgement for a notification ID. Save it to that notification row. Update the impacted-service row only if that notification is still current. Use a conditional update or row lock so an acknowledgement and timeout cannot advance the same service at the same time.
  7. Handle the final layer. If nobody acknowledges the last layer, stop advancing and follow the configured policy, such as retrying, notifying a fallback team, or asking for manual intervention.
Transaction boundary

Assume the outbox, state tables, and processed-event table share a transactional database. Database changes commit together; queue and external-provider calls happen outside those transactions, so stable IDs and idempotent retries are needed.

Non-Functional Requirements

Availability

The scheduling service runs in the control plane. Scheduling work can be deferred during an outage, so the service can target 99.9% availability (about 8 hours and 46 minutes of downtime per year, or roughly 44 minutes per month).

The escalation engine needs higher availability because service owners must be notified quickly during an outage. It should target at least 99.99% availability (a maximum of about 53 minutes of downtime per year, or roughly 4.4 minutes per month).

The scheduling service produces an artifact used by the escalation engine. Replicate this artifact so it remains available to the escalation engine even when the scheduling service is down.

Consistency

Updates to the same service and shift must be applied sequentially when multiple people edit concurrently. No shift should be left unmanned, so schedule writes require strong consistency.

Updates to read replicas can be asynchronous and eventually consistent, allowing the escalation engine to read a stable schedule snapshot while a schedule is being updated.

Resource Contention

When multiple users edit the same service schedule concurrently, the system must ensure that updates are applied sequentially. Use a versioning mechanism to prevent concurrent writes from causing conflicts or leaving shifts unmanned.

Read/Write Ratio

Scheduling service: For a simple logical-operation estimate, assume each service's roster is generated four times a year and looked up once for the initial layer during one incident each month. That is about 12 roster reads for 4 schedule generations, or a baseline 3:1 read-to-write ratio. This counts each roster generation as one logical write, not the individual roster rows. Incidents that reach more layers add roster reads. UI loads, edits, and other reads are also excluded. Use 100:1 as a provisional overall planning estimate that includes expected UI reads and schedule edits; validate it against measured or expected traffic.

Escalation service: A single read-to-write ratio is not useful without specifying how many services an incident affects, how many layers are reached, and how many retries or acknowledgements occur. Estimate reads and writes per affected service and per layer, as in the scale example below.

Scale

Assume 100 organizations with 1,000 services each: 100,000 services requiring rosters. If roster creation happens every three months, the expected scheduling and incident workloads are:

Schedule creation

  • 100,000 roster requests every three months.
  • For this estimate, assume 3 layers, 2 shifts per layer, about 100 days of coverage, and exactly one roster row per layer, shift, and day. This simplifies to about 600 roster rows per service refresh; partial shifts and different rotation lengths could change the count.
  • 600 × 100,000 ÷ 3 ≈ 20 million roster rows per month, or about 7.7 writes per second averaged over a 30-day month.

Average throughput can hide the peak. If all 100,000 services refresh at the start of a quarter, that is about 60 million roster rows in one refresh window. Queue the work and control its processing rate based on the required completion time. Publish each completed roster atomically so the escalation service never reads a partial schedule.

Incident processing

For a rough upper-load scenario, assume 100,000 incidents per month and that each incident affects 100 services and reaches all 3 layers. Per incident, estimate:

  • 1 incident row, plus 1 impacted-service row for each of the 100 affected services.
  • For each affected service: up to 3 roster reads, 3 notification-row writes, 3 acknowledgement/deadline updates, and 3 outbox-event writes (the initial event plus up to 2 delayed escalations).

This is about 1,301 database operations per incident (1 + 100 × (1 + 3 + 3 + 3 + 3)). At 100,000 incidents per month, that is about 130 million operations per month, or roughly 50 per second averaged over a 30-day month. This is a simplified estimate: it excludes event-processing records, outbox dispatch updates, external provider calls, retries, and uneven traffic, so production capacity will need headroom.

A broad cloud-provider outage could affect many services across many tenants at once. Consider tenant-based partitioning and tenant-service keys to make affected on-call data easier to find.

Reliability Considerations

Atomicity

Save related database changes in one transaction. Use an outbox row in that same database transaction to record events that need publishing. The worker publishes the event afterward; the database and queue cannot commit as one transaction, so retries and idempotent consumers handle failures between those steps.

Idempotency

Give every event and notification a stable ID. If a message is delivered again, use that ID to detect it and avoid repeating the database changes. When sending notifications, pass the notification ID as the provider's idempotency key if the provider supports it. Without provider-side idempotency, a retry after an uncertain delivery may send a duplicate notification.

Schedule-generation requests can arrive in bursts. Queue them and process them at a controlled rate. Use a stable event ID so a retried request cannot generate a second roster.

End-to-End Workflow

Schedule generation runs ahead of time and produces the roster. The escalation service reads that roster when an incident occurs.
